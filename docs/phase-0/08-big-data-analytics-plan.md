# Big Data Analytics & PySpark Architecture Plan

## 1. Academic & Technical Justification for Apache Spark

In enterprise and modern institutional software, intelligent assistant systems generate continuous high-velocity telemetry logs (conversational traces, vector retrieval scores, model latency percentiles, user feedback, and failed queries). 

### Why Apache Spark (PySpark) is Appropriate:
1. **Separation of Operational RAG from Analytical Processing:** The real-time conversational endpoint (FastAPI) must remain lightweight and responsive. Offloading heavy analytical aggregations to an asynchronous PySpark batch processing pipeline ensures the user-facing application is never blocked.
2. **Demonstration of Distributed Data Engineering:** PySpark provides an authentic demonstration of big data concepts:
   - Resilient Distributed Datasets (RDDs) and DataFrames.
   - Schema enforcement on semi-structured JSON Lines logs.
   - Distributed aggregation, window functions, and Spark SQL transformations.
   - Generation of optimized analytical artifacts (Parquet columnar storage and aggregated KPI summary tables).
3. **Realistic Scale Demonstration via Partitioned Log Batches:** While running in `local[*]` mode on a student laptop, PySpark utilizes all available CPU cores in parallel to process simulated high-volume institutional interaction histories (10,000 to 100,000+ interaction events).

## 2. Telemetry Logging Architecture & Category Separation

To maintain strict data integrity and prevent synthetic demonstration data from ever being misrepresented as real student usage, the telemetry pipeline categorizes every interaction event into one of **four explicit telemetry sources**:

1. **`REAL_APPLICATION`:** Genuine user interactions originating from the student or admin web interface during active deployment.
2. **`SYNTHETIC_SIMULATION`:** High-volume simulated query batches generated by `scripts/generate_telemetry_dataset.py` for distributed PySpark load testing.
3. **`EVALUATION_BENCHMARK`:** Automated test runs executed by the offline benchmarking harness (`scripts/run_evaluation_benchmark.py`).
4. **`ERROR_DIAGNOSTIC`:** System-level exception traces, model timeouts, and document extraction errors recorded for debugging.

```
[Student / User Interaction] ────────► [FastAPI Backend] ──► Tag: REAL_APPLICATION
[Synthetic Volume Generator] ────────► [Script Trigger]  ──► Tag: SYNTHETIC_SIMULATION
[Automated Evaluation Suite] ────────► [Harness Runner]  ──► Tag: EVALUATION_BENCHMARK
                                                │
                                                ▼ (Asynchronous JSONL Append)
                                [/logs/telemetry/query_events_YYYY_MM_DD.jsonl]
                                                │
                                                ▼ (Batch Trigger: PySpark Local[*])
                                      [Apache Spark Engine]
                                                │
                                                ▼ (Filtered Aggregations by Source)
                                [/data/analytics_summary.json / SQLite Table]
                                                │
                                                ▼
                         [Admin Dashboard: Clearly Labeled Data Provenance]
```

## 3. High-Volume Telemetry Simulation Engine

To thoroughly exercise PySpark’s distributed processing capabilities during academic evaluation and defense, a synthetic log generator (`scripts/generate_telemetry_dataset.py`) will be provided:
- Generates configurable batches of **10,000 to 100,000+** realistic user interaction events.
- Injects statistical distributions reflecting real-world university life:
  - Language mix: 50% English, 20% Kannada/Kanglish, 15% Hindi/Hinglish, 10% Telugu/Tenglish, 5% Unknown.
  - Spikes in "Exam Rules" queries during simulated mid-term exam weeks.
  - 8–12% simulated "Out-of-Domain" queries triggering fallback flows.
  - Realistic latency tails (p95 / p99).

## 4. PySpark Analytical Workloads & Spark SQL Queries

The PySpark analytics module (`analytics/spark_aggregator.py`) executes 6 core data transformations:

### 4.1 Language Distribution & Trend Analysis
- **Goal:** Compute daily and aggregate query percentages across all 4 languages.
- **Spark SQL Expression:**
  ```sql
  SELECT detected_language, 
         COUNT(*) AS total_queries, 
         ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER(), 2) AS percentage_share
  FROM query_events
  GROUP BY detected_language
  ORDER BY total_queries DESC
  ```

### 4.2 Knowledge Gap & Unanswered Query Clustering
- **Goal:** Identify topics and document categories that frequently result in fallback responses (`is_fallback = true` or `top_chunk_similarity_score < 0.65`).
- **Spark Transformation:** Aggregates fallback rates per category and extracts common n-grams/keywords from unanswered queries, alerting administrators to missing circulars.

### 4.3 Document Retrieval Frequency & Hotspots
- **Goal:** Calculate which institutional circulars and specific page numbers are accessed most frequently by students.
- **Spark Transformation:** Explodes `retrieved_doc_ids` array, joins with document metadata table, and computes top-10 most cited regulations.

### 4.4 System Latency & Performance Profiling
- **Goal:** Compute statistical latency distributions across query batches.
- **Spark Metrics:** Calculates `avg(total_latency_ms)`, `percentile_approx(total_latency_ms, 0.50)` (p50), `percentile_approx(total_latency_ms, 0.90)` (p90), and `percentile_approx(total_latency_ms, 0.99)` (p99).

### 4.5 User Satisfaction & Feedback Correlation
- **Goal:** Correlate user feedback ratings (Thumbs Up / Down) against retrieval similarity scores and LLM latency to diagnose user dissatisfaction drivers.

### 4.6 Time-Series Query Volume Aggregation
- **Goal:** Aggregate hourly and daily query counts to generate historical activity charts on the admin dashboard.

## 5. Storage and Dashboard Consumption Architecture

To keep the web UI lightning fast:
1. **PySpark Output:** The Spark job writes aggregated summary metrics to a lightweight JSON structure (`data/analytics_summary.json`) and updates an `analytics_cache` SQLite table.
2. **Dashboard Ingestion:** When an administrator opens the Analytics Dashboard, the FastAPI backend reads the cached PySpark output in $<5\text{ ms}$, rendering visual charts, KPIs, and data tables with zero latency.
3. **On-Demand Re-computation:** Administrators can click a *"Run Spark Analytics Job"* button in the dashboard to trigger an asynchronous PySpark batch run over the latest raw logs.
